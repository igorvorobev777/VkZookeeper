# Домашнее задание № 4. Координация распределённых вычислений с Apache ZooKeeper

В работе развёрнут ансамбль Apache ZooKeeper из трёх узлов в Docker, проверена работа кворума и эфемерных узлов, а также реализован отказоустойчивый координатор расчёта комбинаций навыков из ДЗ № 3 с выбором лидера, чекпоинтами и защитой от устаревших записей по эпохе (fencing).

## Содержание репозитория

* `compose.yaml` — описание ансамбля из 3 узлов (`zk1`, `zk2`, `zk3`).
* `conf/` — конфигурационные файлы `zoo1.cfg`, `zoo2.cfg`, `zoo3.cfg`.
* `coordinator.py` — координатор расчёта частот навыков (`kazoo`, чекпоинты, поддержка `FENCING=0` и `FENCING=1`).
* `logs/` — журналы запусков обоих координаторов без защиты и с защитой по эпохе (`no_fencing_coord-1.log`, `no_fencing_coord-2.log`, `fencing_coord-1.log`, `fencing_coord-2.log`).

## Ответы на контрольные вопросы

### 1. Почему серверов в ансамбле три, а не два и не четыре?

Для принятия решений (выборов лидера и подтверждения записей) ZooKeeper требует **кворум** — строгое большинство узлов: $\lfloor N / 2 \rfloor + 1$. Это гарантирует, что при разделении сети (*split-brain*) одновременно не смогут образоваться два независимых кластера с разными лидерами.

* **3 сервера (кворум = 2):** минимальная отказоустойчивая конфигурация. Ансамбль переживает отказ **1 узла** (остаётся 2 из 3).
* **2 сервера (кворум = 2):** не дают отказоустойчивости — выход из строя любого одного сервера сразу лишает кластер кворума, а вероятность отказа системы выше, чем у одного сервера.
* **4 сервера (кворум = 3):** переживают отказ всё того же **1 узла**, что и кластер из 3 серверов (при падении двух узлов остаётся $2 < 3$). При этом растут накладные расходы на репликацию, а при сетевом разделении «2 на 2» не работает ни одна часть. Поэтому выбирают нечётное число узлов ($2f + 1$: 3, 5, 7).

### 2. Почему защиту по эпохе проверяет получатель записи, а не ZooKeeper?

Между моментом проверки лидерства в ZooKeeper и моментом фактической записи в целевое хранилище всегда существует временной разрыв (гонка *Time-of-Check to Time-of-Use*).

Лидер может успешно убедиться в ZooKeeper, что он активен, сформировать запрос на запись и сразу после этого зависнуть (из-за паузы GC, перегрузки CPU или сетевой задержки). Пока он приостановлен, его сессия истекает, и ZooKeeper выбирает нового лидера с новой эпохой. Когда старый лидер просыпается, его запрос всё равно уходит в сторону хранилища — ZooKeeper не стоит на пути данных между клиентом и хранилищем и не может отозвать уже отправленную операцию.

Единственный компонент, который гарантированно видит все записи в момент их применения — это **получатель записи** (хранилище, БД или атомарная проверка `version` на самом узле результата). Он сравнивает эпоху (fencing token) входящего запроса с последней принятой и атомарно отклоняет устаревшую запись от старого лидера.
